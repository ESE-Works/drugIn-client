# 이력서/포트폴리오용 트러블슈팅 정리

drugIn-client 개발 중 발생한 문제와 해결 과정을 이력서/포트폴리오 문장으로 다듬은 내용입니다.

---

## 1. 계약서 사진 업로드 실패 — 3중 원인 진단 및 해결

**면접용 스피치**

> 계약서 사진을 업로드해서 분석하는 기능을 만들었는데, 실제 기기에서 테스트해보니 분석하기 버튼을 눌러도 아무 반응이 없는 문제가 있었습니다. 처음엔 API 요청 필드명이 잘못됐나 싶어서 백엔드 문서랑 하나하나 대조해봤는데, 필드명 자체는 문제가 없었어요. 그래서 네트워크 요청을 직접 까보면서 원인을 좁혀나갔는데, 알고 보니 원인이 하나가 아니라 세 개가 겹쳐 있었습니다. 첫 번째는 axios 인스턴스에 기본으로 걸려있던 Content-Type이 이미지 파일을 보낼 때도 그대로 적용돼서 웹에서는 파일이 제대로 안 실리는 문제였고, 두 번째는 API 명세에 있던 필수 파라미터 하나를 놓치고 있었던 거였고, 세 번째가 진짜 핵심이었는데, GPT-4o Vision으로 이미지를 분석하는 API라 응답이 오래 걸리는데 axios 기본 타임아웃이 10초로 짧게 잡혀 있어서 응답이 오기도 전에 요청이 끊기고 있었던 거였습니다. 그래서 이 세 가지를 하나씩 다 고치고 나서야 실제로 분석 결과가 정상적으로 돌아오는 걸 확인할 수 있었습니다. 이 경험으로 겉보기엔 똑같은 증상이어도 원인이 여러 개 겹쳐있을 수 있다는 걸 배웠고, 하나 고쳤다고 바로 끝났다고 판단하지 않고 끝까지 재현해서 검증하는 습관이 생겼습니다.

**이력서용**

> 계약서 이미지 분석 API 연동 시 "분석 요청이 응답 없이 멈추는" 현상의 원인을 다각도로 진단하여, FormData Content-Type 충돌·필수 파라미터 누락·API 응답 지연 대비 부족한 타임아웃 설정이라는 3가지 원인을 순차적으로 규명하고 모두 해결. 표면적으로 동일해 보이는 실패가 서로 다른 원인에서 비롯될 수 있음을 확인하며 단계적 디버깅으로 문제를 좁혀나감.

**포트폴리오용 상세 버전**

> React Native + axios 환경에서 이미지 업로드 API 연동 후 "분석하기 버튼을 눌러도 반응이 없는" 문제가 발생. 초기에는 API 필드명 오류를 의심했으나 Swagger 문서 대조로 배제하고, ① axios 인스턴스의 기본 `Content-Type: application/json` 헤더가 FormData 전송 시에도 강제 적용되어 웹 환경에서 멀티파트 boundary가 누락되는 문제, ② API 명세상 필수였던 이미지 출처(source) 파라미터 누락, ③ GPT-4o Vision 기반 분석 API의 응답 지연 시간이 axios 기본 타임아웃(10초)보다 길어 응답 전에 요청이 종료되는 문제를 각각 발견 및 수정. 최종적으로 실제 이미지 분석 응답을 정상적으로 수신하는 것까지 확인.

## 2. 프로덕션 환경 CORS 이슈 원인 규명

**면접용 스피치**

> 배포된 환경에서만 API 호출이 실패하는 이슈가 있었습니다. 에러 메시지만 보면 전형적인 CORS 에러였어요. 그런데 이상하게 터미널에서 curl로 같은 API를 호출해보면 멀쩡하게 응답이 왔습니다. 그래서 "어? 이미 고쳐진 건가?" 싶어서 좀 헷갈렸는데, curl이랑 브라우저의 차이가 뭘까 생각해보다가 User-Agent가 다르다는 걸 떠올렸습니다. 그래서 curl 요청에 브라우저인 것처럼 User-Agent 헤더를 흉내내서 다시 보내봤더니, 그때서야 진짜 원인이 보였습니다. 백엔드를 정식 서버가 아니라 ngrok이라는 임시 터널로 배포해두고 있었는데, ngrok 무료 버전이 브라우저로 온 것 같은 요청에는 실제 서버 응답 대신 자체 경고 페이지를 200 응답으로 대신 돌려주고 있었던 거예요. 그 경고 페이지에는 당연히 CORS 헤더가 없으니까 브라우저 입장에서는 CORS 에러로 보였던 거고요. 원인을 알고 나서는 ngrok에서 제공하는 우회 헤더 하나만 추가해서 바로 해결했습니다. 이 일을 겪고 나서 에러 메시지를 곧이곧대로 믿기보다는, 도구(curl)와 실제 사용 환경(브라우저)의 차이까지 의심해보는 습관이 생겼고, 그리고 임시로 쓰던 배포 방식이 이런 예상 못한 문제를 만들 수 있다는 것도 팀에 공유해서 정식 배포 전환을 준비하게 됐습니다.

**이력서용**

> 배포 환경에서만 발생하는 API 호출 실패를 CORS 문제로 오인하지 않고, curl과 브라우저 요청의 차이를 비교 분석하여 실제 원인이 백엔드를 임시 배포 중이던 ngrok 터널의 경고 인터스티셜 페이지(브라우저 요청에만 응답, CORS 헤더 미포함)에 있음을 규명. 전용 우회 헤더 적용으로 해결.

**포트폴리오용 상세 버전**

> 프로덕션 배포 환경에서만 API 요청이 실패하는 이슈 발생. curl로는 정상 응답을 받아 초기 진단에 혼선이 있었으나, 브라우저의 User-Agent를 재현하여 요청을 보낸 결과 실제로는 CORS 문제가 아니라 백엔드가 임시로 사용 중이던 ngrok 무료 터널이 브라우저성 요청에 한해 경고 인터스티셜 페이지(200 응답, CORS 헤더 없음)를 대신 반환하고 있었음을 확인. `ngrok-skip-browser-warning` 헤더를 추가해 문제를 해결하고, 임시 배포 구조의 구조적 리스크를 팀에 공유.

## 3. 사용자 경험을 고려한 에러 메시지 처리 개선

**면접용 스피치**

> 계약서 분석 기능을 테스트하다가, 어떤 상황에서 요청이 실패했더니 사용자한테 "Cannot POST /contracts/image" 같은 문구가 그대로 토스트 메시지로 뜨는 걸 발견했습니다. 이게 사실 백엔드 프레임워크가 라우트를 못 찾았을 때 자동으로 주는 기본 에러 메시지였는데, 일반 사용자 입장에서는 전혀 이해할 수 없는 내용이잖아요. 그래서 이 문제를 계기로 에러 처리 방식 자체를 다시 봤습니다. 백엔드가 주는 메시지를 그대로 화면에 띄우는 대신, HTTP 상태 코드를 기준으로 저희가 직접 정한 안내 문구를 보여주도록 바꿨어요. 예를 들어 400번대는 "계약서로 인식되지 않았어요" 같은 식으로, 그 외의 경우는 공통적인 재시도 안내 문구로요. 이렇게 하면 나중에 백엔드 쪽 에러 메시지가 바뀌거나 예상 못한 에러가 나도, 사용자 경험은 항상 일관되게 유지될 수 있다는 장점이 있었습니다. 작은 부분이었지만, 에러 상황일수록 사용자에게 어떻게 보여지는지가 중요하다는 걸 다시 생각하게 된 케이스였습니다.

**이력서용**

> 백엔드가 반환하는 원시 에러 메시지(예: 라우팅 오류 문구)가 그대로 사용자에게 노출되는 문제를 발견하고, HTTP 상태 코드 기반으로 매핑한 안내 문구 체계를 설계·적용하여 어떤 에러 상황에서도 일관되고 이해하기 쉬운 메시지를 제공하도록 개선.

**포트폴리오용 상세 버전**

> 계약서 분석 실패 시 "Cannot POST /contracts/image"와 같은 서버 프레임워크의 원시 에러 메시지가 그대로 토스트로 노출되는 것을 확인. 백엔드 응답 내용을 신뢰하지 않고 HTTP 상태 코드(400/503/기타)별로 사용자 친화적인 안내 문구를 매핑하는 에러 처리 로직으로 전면 교체하여, 향후 백엔드 에러 응답이 바뀌더라도 사용자 경험이 흔들리지 않도록 설계.

## 4. 팀 병렬 개발 시 아키텍처 충돌 조정

**면접용 스피치**

> 프로젝트 진행 중에 팀원과 제가 각자 다른 브랜치에서 인증 관련 코드를 동시에 만들고 있었던 적이 있습니다. 저는 토큰 저장이랑 갱신에 집중한 구조를 만들고 있었고, 팀원은 소셜 로그인이랑 사용자 상태 관리를 중심으로 한 구조를 만들고 있었는데, 두 브랜치를 합치려고 보니까 아예 데이터 구조 자체가 달라서 충돌이 났습니다. 이걸 어떻게 합칠지 고민하다가, 저는 기능이 얼마나 완성돼 있는지를 기준으로 삼기로 했습니다. 제가 만든 구조는 토큰 처리는 탄탄했지만 정작 로그인 화면이나 소셜 로그인 연동은 없었고, 팀원 구조는 카카오·구글 로그인이 실제로 동작하고 있었거든요. 그래서 제 구조를 없애는 게 아까웠지만, 이미 동작하는 실사용 기능을 살리는 게 맞다고 판단해서 팀원 구조를 기준으로 통합하고, 제가 만든 코드에서 필요한 부분만 다시 그 위에 얹었습니다. 이 경험을 통해 병렬로 개발할 때는 처음부터 데이터 구조를 맞추고 시작하는 게 제일 좋겠지만, 이미 갈라진 상황이라면 "누가 더 잘 만들었나"가 아니라 "어느 쪽이 실제로 동작하는 기능을 갖고 있나"를 기준으로 빠르게 결정하는 게 중요하다는 걸 배웠습니다.

**이력서용**

> 팀원과 각자 다른 인증 아키텍처(토큰 저장 중심 구조 vs 사용자 상태 중심 구조)를 병렬로 개발하며 발생한 충돌 상황에서, "이미 실사용 기능(소셜 로그인)이 붙어 동작 중인 구조를 우선한다"는 기준을 세워 코드를 통합하고 불필요한 재작업을 최소화.

**포트폴리오용 상세 버전**

> 브랜치 병합 과정에서 본인이 구현한 토큰 전용 인증 구조와 팀원이 구현한 소셜 로그인 연동 인증 구조가 서로 다른 상태 모델을 사용하고 있어 충돌 발생. 두 구조 중 하나를 폐기해야 하는 상황에서, 기능 완성도(이미 동작하는 소셜 로그인 플로우 유무)를 우선 기준으로 삼아 팀원의 구조를 채택하고 본인의 구조를 과감히 폐기, 이에 의존하던 코드를 재정비하여 병합. 자존심보다 실사용 기능을 살리는 방향으로 빠르게 의사결정한 사례.
